# S1: PM GELU→GELU で応答の場を移植する（H5「1 箱の限定」を外す）

箱: PM（Permuted MNIST・1200 枚固定・置換を毎タスク引き直す）の GELU→GELU。エンジンは src/relu_gelu_silu_rl_ext150_0914.py の GPU エンジン（手書き逆伝播。GELU の微分は float32 で z<−14 付近で 0）。neff_pred_0917 が同じエンジンを import して記録と bit 一致で並べ直した実績がある（specs/spec_neff_pred_0917.md §2.1 と §6 S0a）。既知の運命（事後・登録外）: seed 0/1/2 が t66/t68/t117 で偶然水準へ落ちる（vault 測定/GELUとSiLU_s2は150タスクで死ぬか_結果_0915.md §3）。この箱の n_eff は BOX_SPECIFIC だった（測定/機能的応答を他の箱で予測に使う_結果_0917.md）。

設計の骨: resp_ee_0917 の「応答の場の移植」（specs/spec_resp_ee_0917.md §2.2–2.4）をこの箱へ移す。

- 主判定は resp_ee の P1・P2 の相似形。崩壊した網に健康な場を渡すと次タスクを学ぶか（戻す）、健康な網に崩壊した場を渡すと学べなくなるか（奪う）。Adam の初期化／継続の対照は resp_ee の理由づけごと引き継ぐ。ラベルは RESPONSE_BOTH_WAYS / ONE_WAY_RESTORE / ONE_WAY_REMOVE / NEITHER。帯は自然腕の seed 散らばりから導く。

- 分岐点は seed ごとに崩壊時刻で決めるので、腕どうしで見るタスクの置換が違う。開示に書く。
- 崩壊した層がどこか。第2層が µ₂ の壁で −75 まで沈むと読まれているが事後。移植する層を第2層に固定するか、第1層も副で置くか。

## S2: relu_doors に H 単独腕を足す（第一の柱「扉 2 枚」の C の必要性）

```
# S2: relu_doors に H 単独腕を足す（第一の柱「扉 2 枚」の C の必要性）

穴: relu_doors_0919 は ref → C → CH → CHB の梯子で、H だけの腕が無い。「入力の中心化は第1層を救うが網は救えない」「扉 2 枚で足りる」は言えるが、「C は要る」「中間層だけでは足りない」は言えない。主張v11を作って見よう.md の第一の柱の一文目がここに乗る。

箱・エンジン: src/relu_doors_0919.py をそのまま使う（run --arm <腕> --seeds 0-9 --conds raw --tasks 50。腕と扉の対応は DOORS 表、扉の定義は specs/spec_relu_doors_0919.md §2.1）。新しい run id（例 relu_doors_h_<MMDD>）で results/<run>/H に出し、ref・C・CH は results/relu_doors_0919/ の登録済み結果を再利用する。同じエンジンなので S-off の bit 一致検査で再利用の資格を示す。

登録する判定:
- H − ref: H 単独で救うか。ラベル H_ALONE_RESCUES / H_ALONE_FAILS。窓（t31–50 online の seed 中央値）と「窓 ≥ 0.5 の seed 数」を relu_doors と同じ定義で。
- H − CH: C は要るか。C_NEEDED / C_REDUNDANT / TIE。帯は relu_doors の seed 散らばり（CH は 0.986–0.988）から算術で導く。
- 層別の操作確認: H の下で第1層の t1 死亡率（ref は 0.985、C は 0.000）、第2層の z̄₂/sd₂ と gate_zero_frac、|b₂|/sd。per_task.csv の既存列（dead_frac_l1、zbar_l1、zsd_l1、gate_zero_frac_l2、bias_over_sd_l2、r_a1）で足りる。
- 読みの登録: 「C は第1層の扉、H は第2層の扉」という層別の対応が成り立つか。H 単独で第1層が死に、C 単独で第2層が死ぬ、なら成立。

検査: S-off（扉を全部開けると親エンジンと bit 一致）は relu_doors の checks を流用。H 単独の操作確認（a₁ の平均が EMA の遅れの上界内で 0）を変異対照つきで。S-resume（扉 H の EMA が ckpt に入っていること。relu_doors で一度壊れていた）。

費用: 1 腕 × 10 seed。relu_doors は 1 腕（10 seed 束ね）の 50 タスクが 25〜30 分。

起案セッションの Claude の予測: H_ALONE_FAILS 0.8（raw 入力のまま第1層が t1 で死ぬのは H で変わらない）、C_NEEDED 0.8、「C は第1層・H は第2層」の層別対応 0.7。
```

## S3: CH と CHB を 200 タスクへ延ばす（遅延か治癒か）

```
# S3: CH と CHB を 200 タスクへ延ばす（遅延か治癒か）

穴: condA では中心化は LoP を遅らせただけだった（vault ハブ/論点マップ.md §22b: 両層中心化が 5M で悪化、オラクル中心化は b 経路で全滅。引用禁止.md B「centering を完全にすれば防げる」と書かない）。RL-CIFAR の CH は 50 タスク・1.5M 更新で低下ゼロだが、同じ走で B_ROUTE が BIAS_TAKES_OVER（|b₂|/sd 0.002 → 0.181）で、condA を殺した bias 経路が動き出している。「1M で立てた結論は 5M で一度確かめる」は自分たちの運用則（論点マップ §22b）。

設計の骨: relu_doors_0919 の CH と CHB の t50 の ckpt を延長する。退避先 /home/issan/Projects/obsidian-research-data/relu_doors_0919/results/relu_doors_0919/{CH,CHB}/ckpt.pt（results/relu_doors_0919/backup_manifest.json の sha256 で照合）。新しい results/<run>/ にコピーし、src/relu_doors_0919.py の resume で t51–200 へ延長する。engine の docstring どおり完了した走の ckpt は延長でき、S-resume が bit 一致を保証する。CHB は provenance.json の door_lam と同じ λ を渡す。延長の最初のタスクが元の t50 状態から続くことを sha256 で記録する。10 seed のまま。

登録する判定は「落ちるか」でなく「どの型で落ちるか」。腕ごとに 3 型:
- HOLDS: t181–200 の窓が CH の t31–50 の帯の内側。
- GENTLE: 窓は下がるが崩壊線の上。第2層の dead_frac と gate_zero_frac が t50 から増えず、z̄₂/sd₂ が崩壊線を割らない。緩やかさの帯は幅経路 ω から算術で導く。ω ≈ lr/‖W̃ᵢ‖、目減りは ω が半分になるごとに約 1 pt（vault 測定/回る速さが幅の正体か_結果_0912.md）。箱が違うので桁の目安として使い、帯の導出を書く。
- COLLAPSE: 窓 < 0.5、または z̄₂/sd₂ が崩壊線を割る。崩壊線は relu_doors §0 の −1.6 を再導出して使う。
二腕の組合せで主ラベル: CH も CHB も HOLDS か GENTLE → CURED_200（ω 型なら OMEGA_ONLY を併記）。CH だけ COLLAPSE → B_ROUTE_DELAY。両方 COLLAPSE → OTHER_ROUTE。
登録する診断: dead_frac_l2、gate_zero_frac_l2、zbar_l2/zsd_l2、bias_over_sd_l2、w_norm_l1/l2、r_a1、ω。per_task.csv に無い列は足す。足した列は既存の t1–50 の列と bit 一致を保つ。

検査: 延長の連続性（t50 の状態 sha256）、S-resume、追加列の変異対照、扉の操作確認（CHB の |z̄₁| の釘付け）。

費用: relu_doors は 1 腕（10 seed 束ね）の 50 タスクが 25〜30 分。150 タスク分 × 2 腕で 2.5〜3 時間。GPU を占有するので、このマシンの他の走と並べない。

起案セッションの Claude の予測: CURED_200 かつ OMEGA_ONLY 0.55、B_ROUTE_DELAY 0.30、OTHER_ROUTE 0.15。CH の t181–200 は t31–50 から 1〜2 pt 以内の低下。
```
