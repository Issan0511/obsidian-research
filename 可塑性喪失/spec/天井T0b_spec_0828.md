## 1. 前身が未解像で終わった理由

T0 の主観測量は「帯平均折れ線の、最も x が大きい下降根の座標」だった。これは max 型の統計量であり、曲線の値に対して不連続である。

`curves.csv` から算数で確認できる事実として、`z_F` = 0.6630 は帯 [0.6,0.7) の単帯ブリップの右肩の補間座標であり、`z_D(1)` = 0.2729 は帯 [0.2,0.3) の単帯ブリップの右肩である。この 1 帯の符号が seed 再抽出で転ぶと、主根はそれぞれ 0.0653 / 0.0754 の次の根まで飛ぶ。bootstrap 分布が多峰になり、percentile CI が峰の間の距離を測る。

**結論**: `NO_RESOLVED_*` は対象の性質ではなく推定量の性質だった。データは無傷である（k=40 の D は上側の全ガード帯で同符号、根存在率 1.0000、`S_one` PASS）。

## 2. 主観測量

### 2.1 ペアレベルの量

前身と同一定義を使う（`analysis/ceiling_t0/ceiling_t0.py` L165–177 と同値）。

- `x := cos_u_mu · w_norm`
- `F_0 := F_gate`（ペア始点）
- `D_k := (x_{t+k} − x_t) / k`
- **`H_k := D_k − F_0`**
- `F_path := (1/k) Σ_{u=0}^{k−1} F_gate(t+u)`（既存列。§5 の分解に使う）

### 2.2 主統計量

**窓** `W := { ペア | 始点 x ∈ [+0.1, +0.9) }`。

seed `s` について `m_s(k) := mean{ H_k | W かつ 母集団A }`（seed 内はペア重み）。
点推定 `M(k) := mean over 寄与 seed of m_s(k)`（**seed 等重み**。前身 `aggregate_curves` の慣行と一致）。

**主判定量は `M(40)`。**

#### 重み付けを seed 等重みに固定する理由

窓内ペア数は seed 別に 10,713〜27,899 と **2.6 倍**散っている（実測、§3.2）。ペア等重みにすると最多 seed が最少 seed の 2.6 倍の発言力を持つ。

seed 等重みを主に置くのは、**seed が実験の独立単位だから**である。同一 seed 内のペアは同じ 1 本の学習走から出ており互いに独立でない。ある seed が偏った走り方をすれば、その seed のペアは一斉に同じ方向へ寄る。ペア等重みはこの偏りをペア数ぶん増幅し、実質 10 本しかない独立観測を 16 万本あるかのように扱って CI を不当に狭める。bootstrap が seed クラスタである以上、点推定の重みも seed 単位に揃える。

ペア等重みは §5-5 の感度としてのみ報告する。**結果を見た後にペア等重みへ乗り換えない。**

### 2.3 帯を主判定から外す

窓平均はペア集合の上で直接定義され、帯グリッドを経由しない。帯（幅 0.1）は前身で根を取るためだけに必要だった補助構造であり、主判定から外す。帯別値は §5 の記述としてのみ残す。

### 2.4 なぜホライズン判定が畳まれるか

[[論点マップ]] §14 の恒等式と `S_one` の実測により、**k=1 では `H_1 ≡ 0`**（1-step では力＝期待変位）。したがって前身の `P_g = g(40) − g(1)` に相当する量は `M(40) − M(1) = M(40) − 0 = M(40)` に一致する。

**ホライズン判定は主判定に吸収される。** 別立ての `T0_horizon` は置かない。ただし `M(1)` は §4 のベースライン健全性ゲートとして必ず算出する。

### 3.1 窓端の決め方（結果非依存であることの明示）

`[+0.1, +0.9)` の両端は **`band_counts.csv` の support 情報のみ**から決めた。

### 3.2 ガード閾値の根拠（起草時に一度誤ったので記録する）

起草の初稿では窓レベルのガードを「10/10 seed」と書いた。**訂正した。**理由は 2 つ。

- **腕E では発火しない。** 窓内ペア数を実測すると seed 別に 10,713〜27,899 で、全 seed が 300 を大きく超える。窓上端 +0.9 を「ガードが落ちる直前」に置いた以上、窓は定義上「全 seed が寄与する領域」であり、10/10 は自動的に満たされる。**発火し得ないガードは保護になっていない**
- **腕C では単一障害点になる。** 新 seed のうち 1 本でも窓内ペアが 300 を割ると、事前登録腕全体が `INCONCLUSIVE_GUARD` で無効になる。10 本走らせて 1 本の事故で全滅する設計は事前登録腕として脆い

T0 と同じ `≥ 8` に戻し、代わりに**寄与 seed 数を出力に必ず残す**ことで「守る」と「死なない」を両立させる。

## 4. 判定

判定は §6 preflight と §7 構造アサーションを**すべて通過した場合のみ**行う。CI は §3 の seed クラスタ bootstrap による 95% percentile CI。

### 4.1 ベースライン健全性ゲート

| 条件 | 帰結 |
|---|---|
| `M(1)` の 95% CI が 0 を含む | ゲート通過。主判定へ進む |
| `M(1)` の 95% CI が 0 を外す | **`INVALID_BASELINE`。主判定を出さない。** 定理により `H_1 ≡ 0` なので、これは現象ではなく計装バグの検出である |

### 4.2 主判定

| 条件 | `T0b_window` |
|---|---|
| ガード未達 | `INCONCLUSIVE_GUARD` |
| `M(40)` の 95% CI 全体が 0 より大きい | `H_POSITIVE` |
| `M(40)` の 95% CI 全体が 0 より小さい | `H_NEGATIVE` |
| 95% CI が 0 を含む | `NO_RESOLVED_WINDOW_H` |

**語の意味**: `H_POSITIVE` は「実現変位が始点の力の予言より上向き（＝押し戻しが予言より弱い）」、`H_NEGATIVE` は「予言より下向き（＝押し戻しが予言より強い）」。`NO_RESOLVED_WINDOW_H` は等価性の確定ではない。「差がない」とは書かない。

腕E の判定語は `EXPLORATORY_H_POSITIVE` のように接頭辞を付ける。

## 5. 副次量（報告するが判定しない）

1. **k プロファイル**: `M(k)`, k ∈ {1,2,5,10,20,40} と各 CI。単調性は記述であり判定条件にしない
2. **経路分解**: `H = (F_path − F_0) + (D_k − F_path)`。窓平均で両項を報告する。前項は「進むほど力が変わる」ぶん、後項は「ゲート・吸収・符号打ち消し」ぶん。**どちらが主かを事前に予言しない**（起草者は既存データで両項を見ているため）
3. **帯別内訳**: 窓を構成する各帯の `n_pair` / `H` / 分解 2 項
4. **ブリップ寄与**: 帯 [0.6,0.7) を除いた窓平均との差。前身の主根が同帯に支配されていた度合いとの対比として記述
5. **感度**: 窓端を ±1 帯動かした場合、母集団 A_no_near、seed 等重みでなくペア等重みにした場合の 3 つ
6. **選抜チャネル**: 窓内 strict off 件数と、それを除外した場合の窓平均
7. **等調零点（幾何の記述・判定に使わない）**: 上側窓の帯別 `F` と `D_k` に単調減少の isotonic 回帰（PAVA）をかけ、均した曲線の一意な下降交点 `z̃_F`, `z̃_D(k)` と、その差 `g̃(k) := z̃_D(k) − z̃_F` を報告する。seed クラスタ bootstrap の CI も併記する
   - **目的**: [[論点マップ]] §14 の「二種類のゼロ点」の図を支える数字を残すこと。主判定（§2）は量であって位置ではないため、位置の言葉はここでしか出ない
   - **前身との違い**: 単帯ブリップは単調性違反として隣接帯にプールされ吸収される。前身で `z_F` を支配していた帯 [0.6,0.7) の孤立した正は、isotonic 後には消える
   - **限界を必ず明記する**: 交点座標は依然として準 max 型であり、`F` のゼロ近傍（帯 [−0.1,+0.1)、値が +4e-6 台の平坦域）を横切る脆さは isotonic では消えない。CI は主判定より裾が重くなる。**`g̃` の CI が 0 を外しても「分離が示された」とは書かない**

## 6. 推定量の事前検証（preflight）— 実データより先に走らせる

**前身の失敗は構造監査では捕まらなかった。** 構造確認表 A1–A13 は全項目通過した上で、推定量が脆かった。したがって本 spec は構造監査に加えて**推定量そのものの検査**を事前登録する。

以下は合成データに対して実行し、`preflight.csv` に記録する。**実データのロードより前に実行し、1 項目でも FAIL なら実データへ進まない。** FAIL 時に直すのは推定量であって判定基準ではない。

| # | 検査 | 手続き | 合格条件 |
|---|---|---|---|
| P1 | 植え込み回収 | 窓内の H に既知の定数 `h* = 1e-4` を加えた合成 seed 群を作り、推定量を通す | `M(40)` の点推定が `h*` を ±10% で回収し、CI が `h*` を含む |
| P2 | ヌル | H をペア単位で符号ランダム化した合成データを 200 反復 | `NO_RESOLVED_WINDOW_H` 以外を返す割合 ≤ 0.07（名目 0.05 に対する許容） |
| P3 | ブリップ耐性 | 実データと同じ帯構成で、1 帯だけ符号を反転させ大きさを実測ブリップ相当（3e-4）にした合成データ | 窓平均の変化が絶対値で 15% 未満 |
| P4 | seed 欠損耐性 | 10 seed から 1 seed を抜く 10 通り | `M(40)` の符号が全通りで一致（不一致なら記述に格下げする旨を記録） |
| P5 | 前身との整合 | 合成ではなく、既存 `curves.csv` の帯別 H とペア数から再構成した窓平均が、新実装の帯別出力と一致 | 相対差 < 1e-9 |

P3 の閾値 15% は「前身の主根がブリップで 0.6 / 0.93 ≒ 64% 動いた」ことへの対比として設定した。

centered は将来「µ を潰すと天井構造は消えるか」という**負の対照**としては価値がある。その場合は別 spec を立て、判定を「消える」側に置く。本 spec には入れない。

### 8.4 腕E と腕C が食い違った場合の報告規則

**腕C を正とする。腕E との差は「seed 群間変動」として記述に留め、どちらが正しいかを議論しない。**

理由: 腕C のみが予言→検証の形を持つ。腕E のペア数が多いことは検出力の話であって、事前登録の話ではない。

| 腕C | 腕E | 報告 |
|---|---|---|
| 有意 | 同符号で有意 | 通常どおり腕C を主として報告。腕E は一致として併記 |
| `NO_RESOLVED_WINDOW_H` | 有意 | **「事前登録腕では支持されなかった」と報告する。**検出力・ペア数を理由に腕E を採用しない |
| 有意 | `NO_RESOLVED` | 腕C を報告。腕E は探索として併記 |
| **符号が反転** | **符号が反転** | **隠さず報告する。**「窓内 H の符号が seed 群で反転する」は天井の描像に対する独立の発見であり、別 note を立てて追う |
| どちらも `NO_RESOLVED` | 同左 | 未解像として報告。窓・k・閾値を動かして再挑戦しない（§11） |

**この段落は両腕の結果を見る前に確定している。**

## 10. 解釈の上限

### 言えること（腕C 通過時）

- condA・w100・T=10⁴・batch=1・std・境界前窓・k ≤ 40 における、上側窓 `[+0.1,+0.9)` での実現変位と始点予言力の平均差の符号と大きさ
- その差が `F_path − F_0`（力の変化）と `D − F_path`（ゲート・吸収・打ち消し）にどう配分されるか（記述）

### 言えないこと

- 力のゼロ点と変位のゼロ点の**位置**を判定として主張すること（§5-7 の等調零点は記述であり、判定を通していない。§14 の幾何の図はこの記述で支えるが、「位置差が示された」とは書かない）
- 天井が `|F_self|/|F_rest| = 1` であること
- Δ1000 の既知の符号逆転の説明
- 選抜と道のりの因果的二分
- Q17 の `F_rest` 対称性
- centered・他の w・他の T・他の batch・他のデータセットへの一般化
- 真の介入効果

## 11. 実行順序

1. 本 spec を Issa が確認し、vault へ凍結 commit（commit id を `provenance.json` に固定）→ **完了: `b44078c`**
2. 腕C の走行コストを smoke（1 seed）で実測し、着手判断の材料にする

6. 結果を [[論点マップ]] §14 と後継測定 note へ転記
7. 結果を先生へ報告（§12 の判断により事前提案でなく事後報告とする）
8. 本 spec を `spec/実行済み/` へ `git mv`

preflight・アサーション FAIL 時は実装を修正して同じ spec で再実行できる。**主判定量を見た後に窓・k・ガード・閾値を変更しない。**変更が必要なら本 spec を失効させ、新しい版を別ファイルで事前登録する。
